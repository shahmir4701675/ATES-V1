## Batch 1 implementation (21 November 2026)

- **B012:** real spawned timetable/exam processes, at most two per API process. Only the authenticated initiating Coordinator may cancel a run. The durable run state fences result persistence before process termination; cancellation returns confirmed stop or HTTP 202 pending acknowledgment. A successful commit wins a cancellation race and returns HTTP 409 to a later cancel. Completed schedules remain untouched.
- One monotonic budget includes queued time, process startup, input capture, model construction, all CP-SAT searches/diagnostics, extraction, independent validation and saving. Search reserves validation/persistence time. The child has a database-independent hard deadline timer; the parent also terminates overdue workers. Shared engine budgets cap repeated exam room allocation/backtracking and timetable diagnosis. Expired/cancelled workers cannot commit authoritative results.
- Run completion, entries, snapshot and validation receipt share the existing atomic save transaction, with ownership/state/deadline/lease checks before writes and again before commit. Source freshness and hard validation remain mandatory. Failed/timed-out/cancelled headers use existing Infeasible/interrupted lifecycle values; explicit run metadata distinguishes their causes.
- **B013:** default lifespan initializes the session factory first, then recovers Generating orphans. Legacy runs without ownership recover immediately; durable active leases are respected across API processes. Expired leases/deadlines are recovered idempotently by startup and a one-second reaper. Generated/Published/Archived schedules are excluded.
- **B014:** complete previous timetable is captured and supplied separately to S05, while only locked entries become mandatory placements. Zero/disabled S05 has no optimization reward. Prior entries participate in freshness checking and new immutable snapshots. Exact reviewed B004 → B005 → Batch 1 reader fingerprints preserve old inputs, hashes and receipts; unknown profiles fail closed.
- Frontend Cancel now calls the protected backend endpoint and polls for actual worker acknowledgment. It no longer infers cancellation from stopping local polling.

## Deployment and known limitations

- Apply migration 003 explicitly after existing 001/002, using a reviewed operator-selected database. No migration was run against a user database. Worker generation requires file-backed SQLite or PostgreSQL and a spawn-compatible server launch. Connection settings required by workers must be represented in the database URL.
- PostgreSQL migration/transaction/locking execution and cross-host cancellation: **Not Verified**. No safely isolated PostgreSQL instance was supplied. Real local process cancellation, SQLite serialization, deadline rollback and default lifespan recovery are exercised.
- A crashed supervisor's fresh lease can delay recovery up to 15 seconds plus the one-second reaper interval. Remote cancellation remains pending until the owning supervisor acknowledges; ownership/commit fencing still prevents saving the cancelled result. A crash before acknowledgment can leave stop confirmation unavailable despite terminal state; no PID supplied by a client is ever used to kill a process. Cancellation serializes with capture/save transactions and can wait for database locks. Cross-host deployment requires synchronized UTC clocks for persisted leases/deadlines.
- Concurrency cap is per API process, not a distributed global queue. Reference-size performance, the SRS P-8 20% slowdown benchmark, OS termination latency under resource exhaustion and PostgreSQL/network outage behavior are **Not Verified**. The API's synchronous background handoff supervises I/O only; solver CPU work is in a separate process.
- B004 remains partial: legacy official versions without trustworthy original snapshots still fail closed; no destructive recovery or invented historical context was attempted. B008 publication and other deferred features remain outside this batch.
