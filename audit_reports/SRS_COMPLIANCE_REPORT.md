# ATES SRS compliance audit

Audit date: 21 November 2026 (Asia/Karachi). Audit only; no application fixes implemented.

## Assessment

**Not ready for production, institutional publication, or SRS acceptance.** This is a substantial scheduling prototype with real CP-SAT and DSATUR implementations and a passing supplied test suite. Four critical findings undermine its hard-constraint and security guarantees. Several apparently complete screens are local simulations.

228 traceability items examined: **38 Fully Implemented; 110 Partially Implemented; 22 Missing; 44 Incorrectly Implemented; 14 Not Verified.** These include all 83 FR, 27 UR, 17 UC, 24 hard/soft catalogue constraints, 8 P, 6 SAF, 10 SEC, 9 DB, 9 C and 35 explicitly identified unnumbered quality/UI/documentation/interface/legal/localization/reuse obligations. Supplemental IDs Q/UI/DOC/IF/LEGAL/I18N/REUSE are assigned by this audit, not IDs printed in the SRS. Related UR/UC/FR rows overlap semantically; counts measure traceability coverage, not independent feature volume.

**Overall strict verified-assessment compliance: 38 / (228 - 14) x 100 = 17.76%.** Only Fully Implemented rows receive credit; Partial, Missing and Incorrect receive zero. Not Verified rows are excluded. Here verified means there is sufficient executed or static evidence to assess the row, including evidence that a requirement is absent; it does not mean every assessed feature ran successfully. This is not a test pass rate, confidence interval, effort completion percentage, or weighted acceptance score.

The less overlapping primary functional measure is **16 / (83 - 1) x 100 = 19.51%**. FR totals:16 full,41 partial,11 missing,14 incorrect,1 unverified. No partial-credit inflation is used. Measured source-wide coverage and deployed production compliance remain unknown.

## Architecture actually found

- Frontend: React18, TypeScript, Vite6, TailwindCSS and lucide-react. App.tsx implements a small History-API router and role-menu shell. Pages use services/api.ts, which adapts numeric backend IDs and server schedule types; VITE_USE_MOCK defaults false.
- Backend: FastAPI application factory in backend/main.py, alias backend/app.py; two routers for master data and scheduling.32 OpenAPI paths, plus hidden /api aliases. JSON request/response schemas use Pydantic; database access uses SQLAlchemy.
- Database:21 ORM models and db/schema.sql, PostgreSQL/psycopg2 configuration path and SQLite tests with FK enforcement. No versioned migration directory or actual production schema/grant inspection.
- Timetable: engine/timetable_solver.py creates OR-Tools CP-SAT assignment variables, calls constraint classes, optimizes weighted preferences, then calls TimetableValidator.
- Exams: engine/exam_scheduler.py constructs NetworkX conflict graph, calls greedy_color(strategy='DSATUR'), maps colours/splits room groups, and falls back to integrated CP-SAT session/room assignment; ExamValidator checks candidate results.
- Data boundary: backend/adapter.py converts ORM records into engine dataclasses and persists results transactionally. Solves run after input-read transaction closes. FastAPI BackgroundTasks is used; there is no separately managed worker process or cancellation service.
- Split source of truth: live CRUD/generation/availability/config/read/move calls coexist with local login/users/audit/import/publication/config deletion. A successful mock action is not proof of persisted backend functionality.

## Status interpretation

Fully Implemented requires corroborated implementation plus successful applicable execution for the claimed functional scope, or directly inspectable deterministic behavior with supporting execution (for example schema/OpenAPI construction). It is not a declaration that no latent defect can exist. Partial means concrete clauses are present but others are missing, broken, or not sufficiently validated. Missing means the required authoritative capability is absent, even if a table, button or placeholder exists. Incorrect means observed or established behavior contradicts the requirement. Not Verified is reserved for unmet evidence needs such as production TLS, backups, reference-size timing, browser accessibility or uptime. A full isolated requirement does not waive separate failed security/lifecycle requirements.
