1 Introduction
Preparing course timetables and examination schedules is one of the most error-prone administrative
tasks in a university department. A schedule must satisfy many interacting conditions at once: an
instructor cannot teach two classes at the same time, a room cannot host two sessions at once, a
student batch cannot sit in two places, rooms must be large enough and of the right type, and instructors
have their own availability. When these rules are applied by hand, usually in spreadsheets, clashes are
discovered late and every correction can create new ones.
TheAuto Timetable / Exam Scheduler(ATES) is a web-based application that takes basic institutional
data (courses, instructors, rooms, student batches and time slots) and automatically produces a conflict-
free timetable and examination schedule. The scheduling rules are modelled as a constraint satisfaction
problem (CSP), and the examination schedule additionally uses graph colouring, so that clashes are
removed by construction rather than found afterwards.
This section states the purpose and scope of the document, identifies the stakeholders, describes the
intended readers, and explains the notation used. Section 2 describes the product in general terms.
Section 3 contains the detailed user and system requirements and the behavioural models. Section 4
gives the non-functional requirements, Section 5 specifies the database, and Appendix A is the data
dictionary.
1.1 Document Purpose
This document is the Software Requirements Specification (SRS) for theAuto Timetable / Exam
Scheduler. It covers the complete product: the web user interface, the application programming
interface (API), the scheduling engine and the database. It does not describe a single subsystem in
isolation.
The purpose of the SRS is to identify, document and organise all functional, non-functional and data
requirements of the system so that they are accurate, unambiguous, verifiable and traceable. It is the
agreed basis for design, implementation and testing, and for evaluating whether the finished product
meets the needs of its stakeholders. The document follows the structure of the department’s SRS
template, which is based on IEEE Std 830-1998 and ISO/IEC/IEEE 29148:2018 [1, 2].
1.2 Product Scope
ATES is a scheduling engine with a web front end. Users enter or import institutional parameters,
configure the scheduling rules, and ask the system to generate a timetable or an exam schedule. The
system then displays the result in filterable views, reports any conflicts it cannot resolve, allows controlled
manual adjustment, and exports the final schedule as PDF or CSV.
Objectives and goals.
• Produce complete timetables and exam schedules that contain no violation of the mandatory (hard)
scheduling rules.
• Replace manual, spreadsheet-based drafting with a repeatable process that can be re-run whenever
data changes.
• Explain clearly why a schedule cannot be built when the input data is over-constrained, instead of
failing silently.
• Give each class of user a suitable view of the published schedule (by batch, instructor or room).
Benefits.Coordinators spend less time drafting and correcting schedules; clashes between instructors,
rooms and batches are eliminated by the solver and re-checked by an independent validator; schedule

Term Meaning
Academic term A semester for which one timetable and one exam schedule are produced.
Batch / section A group of students of one programme and admission year (for example,
BSCS 2024, Section A) that attends the same classes.
Conflict A violation of a scheduling rule, such as an instructor or room assigned to two
sessions at the same time.
Course offering A course taught to one batch by one instructor in one term. It is the unit that
is scheduled.
Exam session A date together with a start and end time during which exams may be held.
Graph colouring Assigning a colour to every vertex of a graph so that adjacent vertices differ;
here, assigning exam sessions to courses that share students.
Hard constraint A rule that every valid schedule must satisfy.
Published schedule A schedule approved by the Approver and visible to faculty and students.
Session (class) One scheduled meeting of a course offering (a lecture or a lab block) in a
room and slot.
Soft constraint A preference that the solver tries to satisfy as far as possible; violating it does
not invalidate the schedule.
Time slot One period in the weekly grid, identified by day and slot index.
Version One generated variant of the schedule of a term, identified by a version
number.

2 Overall Description
2.1 Product Perspective
The Auto Timetable / Exam Scheduler is a new, self-contained product. It does not replace a software
system; it replaces the manual practice in which a timetable coordinator drafts timetables and exam
date-sheets in spreadsheets or on paper and then corrects clashes one by one. It is not a member of an
existing product family and is not a component of a larger system in the first release. In a later release it
may be connected to the university’s student information system, which is why all master data is held in
a clean relational schema (Section 5) and can already be imported from CSV files.
ATES is delivered as a web application. Users work in a web browser; the browser communicates over
HTTPS with an application server that exposes a REST API. The server stores all data in a relational
database and hands scheduling problems to a scheduling engine built on constraint programming
(Google OR-Tools CP-SAT) and graph algorithms (NetworkX) [8, 9]. Figure 1 shows the system in its
environment: the people who interact with it and the files that enter and leave it.

3.1.4 Communications Interfaces
All communication between the browser and the server uses HTTP over TLS 1.2 or later (HTTPS).
The API follows REST conventions: resources are addressed by URL, data is exchanged as UTF-8
JSON, CSV files are uploaded with multipart/form-data (maximum 10 MB), and exported files
are downloaded with the appropriate content type. Every request except login carries a JSON Web
Token in the Authorization header. Cross-origin requests are accepted only from the configured
front-end address. Because a generation run can take up to several minutes, the browser starts a run
with one request and polls a status resource every two seconds; no persistent connection is required.
The database connection is internal to the server and uses the driver’s own encrypted or local channel.
Specific cipher suites and token algorithms will be chosen at design time from current recommendations.

4.3 Software Quality Attributes
The most important quality attributes, in order of preference, are:correctness(a published schedule
has no hard-constraint violation),reliability,usability for the Coordinator,maintainability and design
for change, andportability. Where two attributes conflict, the earlier one in this list wins; for example,
the solver is allowed to use its full time limit rather than return an unverified fast answer. Ease of use for
the Coordinator is preferred over ease of learning for occasional users.
4.3.1 Correctness
The correctness of every schedule is established twice: by constructing the schedule from the constraint
model, and by checking it afterwards with a validator that is written independently of the solver model
(FR-6.7). Acceptance requires zero hard-constraint violations on every test dataset, including at least
one generated dataset of the reference size (A-1). A set of unit tests with one deliberately violating
schedule per constraint (H01–H10, E01–E05) shall prove that the validator detects each violation.
4.3.2 Reliability
The system shall complete 99% of generation runs on valid input without an internal error, and shall
report the cause of any failure instead of terminating silently. Database transactions guarantee that a
failure leaves the data consistent (SAF-2). After a server restart, runs that were Generating shall be
marked Infeasible with the reason “interrupted” so that no schedule remains in an undefined state.
4.3.3 Availability
During working hours (08:00–18:00 on working days) the system shall be available at least 99% of the
time, measured per month. Planned maintenance shall be done outside these hours.
4.3.4 Usability
A Coordinator who has read the two-page quick-start guide shall be able to go from an imported dataset
to a generated timetable in under 15 minutes without help. Faculty and students shall find their own
timetable within two clicks after login. Every error message shall say what is wrong and what the user
can do about it. Colour is never the only carrier of meaning (conflicts also carry an icon and text), and
the interface meets WCAG 2.1 level AA contrast.

4.3.5 Maintainability and Design for Change
Scheduling rules change from semester to semester, so the main design aim is that a rule can be added
or changed without touching the rest of the system. This is achieved as follows.
• Constraint modules.Each constraint (H01, S02, E01, . . . ) is a separate class with one shared
interface (add to model, validate, describe). Adding a rule means adding one class and one row in
constraint_rules; no other module changes.
• Layered architecture.The user interface, API, scheduling engine and data access are separate layers
that communicate only through defined interfaces, so each can be tested and replaced independently.
• Configuration instead of code.Slot length, working days, weights, limits and thresholds are stored
as configuration (Appendix A.1), never hard-coded.
•Exporter interface.A new output format is added by implementing one exporter class.
• Standards and tests.Python code follows PEP 8, public functions have docstrings, and at least 70%
of the engine and validator code is covered by automated unit tests.
• Pinned dependencies.Library versions are pinned and recorded so the system can be rebuilt later.
4.3.6 Portability
The server shall run unchanged on Linux and Windows. Because data access uses an ORM, the same
code runs on PostgreSQL and on SQLite; a test run against both databases shall pass before release.
The front end shall work in current versions of Chrome, Firefox, Edge and Safari. The system shall be
packaged so that it can be started with one command (for example, with a container description file).
4.3.7 Testability
Generation shall be repeatable for a given dataset, configuration and seed (FR-6.9), a sample dataset
with expected results shall be delivered, and every requirement shall be written so that a test case can
be derived from it (traceability in Section 3.2.3).
4.3.8 Interoperability
The system shall exchange data only in open formats: UTF-8 CSV for import and export, JSON for the
API with an OpenAPI description, and PDF for printable output. These formats allow a later connection
to the student information system without changing the core.
4.3.9 Adaptability
The system shall adapt to changes in institutional data without code changes. Courses, instructors,
rooms, batches, terms, slot grids, constraint weights and exam rules are all stored as data or configu-
ration (Appendix A.1), so a new semester, a new room or a changed break period needs only a data
update and a new generation run. Existing master data and constraint configurations shall remain
usable after such changes (FR-5.6, FR-9.5).
4.3.10 Flexibility
The system shall allow its requirements to change in future releases at low cost. A new scheduling rule
is added as one constraint module and one row in constraint_rules, a new output format as one
exporter class, and a new user role by extending the role table and the access checks (FR-1.5), without
redesign of the other layers (Section 4.3.5).

4.3.11 Robustness
The system shall keep working correctly when it receives invalid, incomplete or unexpected input. All
input is validated on the server (SEC-6); malformed CSV rows are rejected individually with a reason
and do not stop the import (FR-4.2, FR-4.3); an over-constrained or incomplete dataset produces an

The scheduling engine, the constraint modules, the validator and the CSV import/export components
shall be independent of the web layer so that they can be reused in a command-line tool or in another

Doubling the number of offerings and rooms from the reference dataset shall not require changes to the
design; run times may grow but remain bounded by the configurable time limit (C-4).

5.1.5 Business Integrity Rules
The following rules are enforced by the database where possible and otherwise by the validator of
FR-8.1.
• A room, an instructor and a batch can occur at most once per slot in one timetable version (UNIQUE
constraints ontimetable_entries; hard constraints H01–H03).
• A course occurs at most once per exam schedule (UNIQUE on exam_entries); the seats allocated
to an exam sum to itsstudent_countand never exceed the capacity of the room (E03).
• A user with role Faculty has aninstructor_id; a user with role Student has abatch_id.
• At most one term is Active, and at most one schedule per term and type is Published (FR-9.3).
• Entries of Published and Archived schedules are read-only; changes require a new version (SAF-4).
5.2 Legal and Regulatory Requirements
The system shall comply with the university’s rules on the protection of student and staff records and
shall store only the personal data listed in SEC-10. All third-party libraries shall be used under their
open-source licences (OR-Tools, NetworkX, FastAPI, React and Tailwind CSS use permissive licences),
and licence notices shall be delivered with the software.
5.3 Internationalisation and Localisation
The first release provides an English user interface. All text is stored as UTF-8 so that names in Urdu
script can be stored and shown correctly, and all interface text is kept in a separate resource file so that
an Urdu interface can be added later without code changes. Times use the 24-hour clock and the time
zone Asia/Karachi; the first working day of the week is configurable per term.
